## Язык

Код, комментарии, сообщения об ошибках и документация в этом репозитории — на русском. Придерживайтесь этого стиля: комментарии объясняют _почему_, а не _что_.

## Команды

```bash
pnpm dev                 # web :3000 + api :4000 одновременно (turbo)
pnpm build               # сборка в порядке зависимостей
pnpm typecheck           # tsc --noEmit во всех пакетах
pnpm lint                # eslint во всех пакетах
pnpm format              # prettier по репозиторию

pnpm db:up / db:down     # Postgres в Docker
pnpm db:migrate          # prisma migrate dev (создать + применить)
pnpm db:deploy           # prisma migrate deploy (CI/prod)
pnpm db:generate         # перегенерировать клиент после правки schema.prisma
pnpm db:studio
```

Работа с одним пакетом — через `--filter`:

```bash
pnpm --filter @expense-tracker/api dev
pnpm --filter @expense-tracker/web lint
```

Тесты есть в `apps/api` (jest) и `apps/web` (vitest + Testing Library), в остальных пакетах
задачи `test` нет — `pnpm test` их просто пропускает. Команды запуска отдельных тестов и
нюансы для каждого пакета — в `apps/api/CLAUDE.md` и `apps/web/CLAUDE.md`.

Требования: Node ≥ 20.19 (`.nvmrc` → 24.21.0, `nvm use`), pnpm 8.6+, Docker.

## Состояние проекта

Каркас: схема БД, валидация и контроллеры написаны. `AuthService` (register/login/refresh/logout),
категории и транзакции (доходы/расходы, `TransactionsModule`) реализованы полностью; методы
сервиса budgets остаются заглушками `throw new Error('Не реализовано')`. Реализован health-check.

Фронтенд реализован до главного экрана включительно: Feature-Sliced Design (подробности в
`apps/web/CLAUDE.md`), контур сессии (access-токен в памяти, авто-refresh, guard-редиректы),
страницы `/login`, `/register`, `/dashboard` — рабочий главный экран (сводка за месяц, разбивка
по категориям, лента транзакций с курсорной подгрузкой, фильтры, переключатель месяца,
создание/удаление транзакций и категорий, меню пользователя в шапке), shadcn/ui на Tailwind 4.
`authorizedFetch` используется в реальных запросах (категории, транзакции, сводка). Дальше —
экраны бюджетов.

## Архитектура

Общее для всего проекта — ниже. Бэкенд-специфика (NestJS, Prisma, guard'ы, обработка ошибок) —
в `apps/api/CLAUDE.md`, фронтенд-специфика (Feature-Sliced Design, shadcn/ui) — в
`apps/web/CLAUDE.md`.

### Поток данных: одна Zod-схема на всё

`packages/shared` — единственный источник правды по формам данных. Схема из `packages/shared/src/schemas/` → `createZodDto(schema)` в `apps/api/src/modules/*/dto/` → класс DTO работает одновременно как тип `@Body()`, как правило валидации (глобальный `ZodValidationPipe` в `app.module.ts`) и как источник модели для Swagger. Тот же пакет импортируется фронтендом для типов и валидации форм.

Отсюда следуют два правила:

- Меняя контракт API, правьте схему в `shared`, а не DTO.
- Схемы с `transform` дают **два** разных типа: `z.input` (что шлёт клиент) и `z.output` (что получает сервис после валидации). Формы фронтенда типизируются через `*Input`, сервисы — через `*Data`. См. конец `schemas/transaction.ts`.

### Деньги — строки, не числа

`packages/shared/src/schemas/money.ts` — обязательное чтение перед любой работой с суммами. В БД `Decimal(12,2)`, по сети — каноническая строка `"1234.56"`, арифметика — через `toMinorUnits`/`sumMoney` (в копейках). Сервисы обязаны прогонять `amount` из Prisma через `toMoneyString()` перед отдачей — паттерн в `TransactionsService.serialize`.

### Даты

`isoDateSchema` принимает ISO-строку и отдаёт `Date`. Именно `z.union([...iso...]).transform(...)`, а **не** `z.coerce.date()`: Swagger строится через `z.toJSONSchema()`, а `Date` в JSON Schema непредставим и сборка документа падает.

### Сборка и tsconfig

Внутренние пакеты подключаются как `workspace:*` и потребляются из `dist`, а не из исходников. Порядок обеспечивает Turborepo (`dependsOn: ["^build"]`, `build` дополнительно зависит от `db:generate`). Следствие: после правки `packages/shared` пересоберите его, иначе приложения увидят старые типы (в dev это делает `tsc --watch` из `dev`-скрипта пакета).

`incremental` в `packages/tsconfig/base.json` выключен намеренно: кэш `.tsbuildinfo` от `tsc --noEmit` вместе с `deleteOutDir` в `nest-cli.json` давал молча пустой `dist`. Не включайте обратно.

## Незавершённые задачи

`.claude/TODO.md` — список пунктов, отложенных по объективным причинам (нужна ручная проверка,
доступ, решение пользователя и т. п.), между сессиями. Перед началом новой задачи сверяться
с этим файлом: не относится ли что-то из открытых пунктов к текущей работе, и по возможности
закрыть попутно. Когда работа заканчивается с незавершённым хвостом (пункт плана не проверен,
находка требует отдельного решения) — дописать пункт туда, а не оставлять только в переписке.
Закрытый пункт вычёркивается или удаляется, а не копится.

## Git

`git add` и `git commit` — только по отдельному явному распоряжению пользователя. Завершённая
задача (правка кода, новые файлы) сама по себе не повод стейджить или коммитить — рабочее дерево
остаётся как есть, пока не попросят явно.

### Ветки (GitHub Flow)

- `master` — основная ветка, в неё не коммитят напрямую: любая задача ведётся в отдельной
  ветке, созданной от актуального `master`.
- Именование — `<тип>/<краткое-описание-на-английском-в-kebab-case>`, тип — из типов
  Conventional Commits (`feature` для новой функциональности, `fix` для багфиксов, `docs`,
  `refactor` и т.д.), описание короткое и по сути изменения (например
  `feature/dashboard-screen`, `fix/auth-refresh-loop`). Ветка с планом задачи (`.claude/plans/`)
  называется так же, как план — см. `feature/auth-users-cqrs-jwt`.
- Ветка уходит в PR, когда задача готова к ревью; сливается в `master` после ревью, ветка после
  мержа удаляется.
- Создание веток, PR, мерж в `master` и удаление веток — действия, которые Claude выполняет
  только по явному запросу, как и `git commit`.

### Формат коммитов

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```
<тип>[необязательный скоуп]: <описание>

[необязательное тело]

[необязательный(е) футер(ы)]
```

- Тип и скоуп — фиксированные английские ключевые слова спецификации: `feat` (новая
  функциональность), `fix` (исправление бага), `docs`, `refactor`, `perf`, `test`, `build`, `ci`,
  `chore`, `revert`. Скоуп в скобках — обычно модуль/пакет (`feat(transactions): ...`,
  `fix(api): ...`).
- Описание, тело и футеры — на русском, как весь остальной репозиторий; описание — в
  повелительном наклонении, без точки в конце.
- Ломающее изменение — `!` сразу после типа/скоупа (`feat(transactions)!: ...`) **и** футер
  `BREAKING CHANGE: <что именно и как мигрировать>`.
- Один коммит — одно логическое изменение: не смешивать `feat` и `fix` разных концернов в одном
  коммите, даже если они сделаны в одной задаче.

## Соглашения

- Prettier: одинарные кавычки, `printWidth: 100`, точки с запятой, `trailingComma: all`.
- ESLint (flat config): обязательны inline type imports (`import { type Foo }` / `import type`), `no-console` кроме `warn`/`error`, `eqeqeq: smart`. Для Nest отключены правила о «бесполезном конструкторе» — это parameter properties DI.
- TS строгий, включая `noUncheckedIndexedAccess` и `noImplicitOverride` (отсюда `override canActivate` в guard).

Соглашения по структуре модулей API и по фронтенд-слоям — в `apps/api/CLAUDE.md` и
`apps/web/CLAUDE.md`.

## Планы

Планы заметных задач хранятся в репозитории, в `.claude/plans/`, парой файлов:

| Файл             | Содержимое                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| `<имя>.md`       | сам план: контекст (зачем задача), изменения по файлам, раздел «Порядок работ», раздел «Проверка» |
| `<имя>.tasks.md` | чеклист `- [ ]` по разделам, порядок совпадает с «Порядком работ» плана                           |

Образец — пара `auth-users-cqrs-jwt.md` / `auth-users-cqrs-jwt.tasks.md`.

Чеклист ведётся по ходу реализации (`[ ]` → `[x]`) и коммитится вместе с кодом: план остаётся в истории проекта рядом с изменениями, которые он описывает, а не только в переписке. Внеплановые находки дописываются в конец tasks-файла отдельным разделом — см. раздел 8 в `auth-users-cqrs-jwt.tasks.md`.

Оба файла — на русском, как и весь остальной репозиторий.
