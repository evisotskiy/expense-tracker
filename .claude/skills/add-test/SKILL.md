# Тест на файл

Skill пишет тест и прогоняет его. Не стейджит, не коммитит и не создаёт веток — это отдельные
явные просьбы (`CLAUDE.md`, раздел «Git»). Тест остаётся в рабочем дереве.

## Аргументы

`$ARGUMENTS` — `<путь к файлу>`, относительно корня репозитория или абсолютный.

- Если пути нет — остановиться и спросить, не угадывать цель.
- Если передана папка или несколько файлов — взять файлы по одному; для папки сначала
  перечислить, что в ней нет теста, и уточнить у пользователя, на что писать.

## Порядок

1. Проверки до любых действий:
   - файл существует, это исходник (`.ts`/`.tsx`), а не тест, конфиг, `index.ts`-барель,
     сгенерированный код (`generated/`, `dist/`) или чистые типы без логики — иначе сообщить,
     что тестировать нечего;
   - рядом ещё нет теста (`<имя>.spec.ts` в `apps/api`, `<имя>.test.ts(x)` в `apps/web`). Если
     есть — не перезаписывать: прочитать его, найти непокрытые ветки и **дополнить**; если
     покрыто всё — сказать об этом и остановиться;
   - текущая ветка не `master` — на `master` работа не ведётся (правила в `CLAUDE.md`); при
     `master` предупредить, что тест ляжет в рабочее дерево на мастере, и спросить, продолжать ли.
2. Определить пакет по пути и прочитать его `CLAUDE.md` (`apps/api/CLAUDE.md` или
   `apps/web/CLAUDE.md`) — там нюансы запуска. Для других пакетов (`packages/*`) задачи `test` нет:
   сообщить, что инфраструктуры тестов нет, и не заводить её самовольно.
3. Прочитать целевой файл целиком и **образцы** — 1–2 существующих теста того же вида (см.
   таблицу ниже): повторить их способ мока, структуру `describe`/`it`, стиль названий.
4. Составить перечень поведений до кода: успешный путь, граничные значения, ветки ошибок,
   каждая ветка `if`/`throw`. Тест проверяет поведение, а не пересказывает реализацию.
5. Написать тест рядом с файлом (см. «Куда класть»).
6. Прогнать (см. «Запуск») и убедиться, что тест зелёный. Затем прогнать `typecheck` и
   `lint` пакета: тест не должен ломать их.
7. Проверить, что тест реально что-то ловит: на одном-двух ключевых утверждениях мысленно или
   временной правкой исходника убедиться, что поломка поведения роняет тест. Временную правку
   обязательно откатить (`git diff` исходника должен быть пуст).
8. Отчитаться: путь к тесту, что покрыто, что **не** покрыто и почему.

## Куда класть и как называть

| Пакет      | Файл теста                            | Раннер                   | Образцы                                                        |
| ---------- | ------------------------------------- | ------------------------ | -------------------------------------------------------------- |
| `apps/api` | `<имя>.spec.ts` рядом с исходником    | jest + ts-jest           | `auth.service.spec.ts`, `password.spec.ts`, `duration.spec.ts` |
| `apps/web` | `<имя>.test.ts(x)` рядом с исходником | vitest + Testing Library | `month.test.ts`, `transaction-form.test.tsx`                   |

Образцы по виду кода: чистая функция — `duration.spec.ts` / `month.test.ts`; сервис Nest —
`transactions.service.spec.ts`; React-компонент — `*.test.tsx` в том же слое FSD.

## Конвенции

- Язык: названия `describe`/`it`, комментарии и сообщения — на русском; комментарий объясняет
  _почему_ проверяется именно это, а не _что_ делает строка.
- Стиль кода — по `CLAUDE.md`: одинарные кавычки, `printWidth: 100`, точки с запятой,
  `trailingComma: all`, inline type imports (`import { type Foo }`), без `console.log`.
- Деньги — только строки (`"1234.56"`), сравнивать строки, не числа; прочитать
  `packages/shared/src/schemas/money.ts` перед тестами на суммы.
- Даты — фиксировать явно (`new Date('2026-01-31T23:50:00Z')`, fake timers), не зависеть от
  «сейчас».
- Тесты изолированы: без сети, без реальной БД, без общего состояния между `it`. Зависимости
  сервиса (`PrismaService` и т.п.) — моки в стиле соседних `*.service.spec.ts`.
- `apps/web`: запросы пользователя — через `userEvent` и роли/подписи (`getByRole`,
  `getByLabelText`), не через классы и `data-*`; импорты слоёв — по правилам FSD (только вниз,
  слайс — корнем), иначе упадёт eslint.
- Не менять исходник ради теста. Если код нетестируем без правки (скрытая зависимость,
  побочный эффект при импорте) — написать, что именно мешает, и предложить правку отдельно.
- Не добавлять зависимости и не трогать конфиги раннеров.

## Запуск

```bash
# apps/api — один файл
pnpm --filter @expense-tracker/api exec jest <путь относительно apps/api/src>

# apps/web — только через turbo (иначе нет собранного packages/shared/dist)
pnpm turbo run test --filter=@expense-tracker/web -- <путь к тесту>

pnpm --filter @expense-tracker/<api|web> typecheck
pnpm --filter @expense-tracker/<api|web> lint
```

## Сценарии отказа

Остановиться на первом сработавшем и сообщить причину; не писать тест «на всякий случай».

| Ситуация                           | Как определить                                     | Что делать                                                                                                                    |
| ---------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Нет аргумента                      | `$ARGUMENTS` пуст                                  | Спросить путь, не угадывать                                                                                                   |
| Файл не найден                     | `Read`/`Glob` не находят путь                      | Показать ближайшие совпадения по имени, спросить, какой имеется в виду                                                        |
| Нечего тестировать                 | типы, барель, конфиг, generated                    | Сообщить причину, ничего не создавать                                                                                         |
| Пакет без тестового раннера        | путь в `packages/*`                                | Сообщить, что задачи `test` нет; не заводить раннер самовольно                                                                |
| Тест уже есть и покрывает всё      | непокрытых веток не найдено                        | Сообщить и остановиться                                                                                                       |
| Код нетестируем без правки         | нужен рефакторинг исходника                        | Описать препятствие, предложить правку, ждать решения                                                                         |
| Тест падает из-за бага в исходнике | утверждение верное по смыслу, код ведёт себя иначе | Не подгонять тест под баг: показать расхождение и спросить, что считать верным; при необходимости — пункт в `.claude/TODO.md` |
| Тест красный по неясной причине    | после двух попыток исправления                     | Показать вывод jest/vitest целиком, не оставлять сломанный тест как «готовый»                                                 |

## Ограничения

- Не использовать `.skip`, `.only`, `xit`, `--passWithNoTests`, ослабление утверждений и
  `any`/`@ts-ignore`, чтобы «позеленить» тест.
- Не придумывать результаты: в отчёте — только то, что реально запускалось в сессии. Если
  `typecheck` или `lint` не прогонялись — так и написать.
- Не стейджить и не коммитить; для коммита — отдельный `/commit`.
- Если появляется незакрытый хвост (непокрытая ветка, найденный баг, нужна правка исходника) —
  дописать пункт в `.claude/TODO.md`, а не оставлять только в переписке.
