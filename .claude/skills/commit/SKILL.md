# Коммит

`git add` и `git commit` выполняются только по явному распоряжению пользователя — вызов этого
skill и есть такое распоряжение. Сам по себе завершённый код не повод коммитить.

## Порядок

1. `git status` и `git diff` (staged + unstaged) — понять, что именно меняется.
2. Разбить изменения на логические коммиты: один коммит — одно логическое изменение, не смешивать
   `feat` и `fix` разных концернов, даже если они сделаны в одной задаче.
3. Стейджить файлы поимённо (не `git add -A`), чтобы не захватить лишнее (`.env`, артефакты сборки).
4. Составить сообщение по формату ниже и закоммитить.
5. `git status` — убедиться, что коммит прошёл и в дереве нет забытых файлов.

## Формат

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```
<тип>[необязательный скоуп]: <описание>

[необязательное тело]

[необязательный(е) футер(ы)]
```

- Тип и скоуп — фиксированные английские ключевые слова спецификации: `feat` (новая
  функциональность), `fix` (исправление бага), `docs`, `refactor`, `perf`, `test`, `build`, `ci`,
  `chore`, `revert`. Скоуп в скобках — обычно модуль/пакет (`feat(transactions): ...`,
  `fix(api): ...`).
- Описание, тело и футеры — на русском, как весь остальной репозиторий; описание — в
  повелительном наклонении, без точки в конце.
- Ломающее изменение — `!` сразу после типа/скоупа (`feat(transactions)!: ...`) **и** футер
  `BREAKING CHANGE: <что именно и как мигрировать>`.
- Один коммит — одно логическое изменение: не смешивать `feat` и `fix` разных концернов в одном
  коммите, даже если они сделаны в одной задаче.

## Ограничения

- Не коммитить напрямую в `master` — сначала нужна отдельная ветка (правила веток — в `CLAUDE.md`,
  раздел «Git»). Если текущая ветка `master`, остановиться и сообщить пользователю.
- Не использовать `--no-verify`, `--amend` и force-push без отдельной просьбы.
- Если pre-commit хук упал — исправить причину и создать новый коммит.
