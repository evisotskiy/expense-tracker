# Pull request

Создание PR — действие, которое выполняется только по явному запросу (правила — в `CLAUDE.md`,
раздел «Git»); вызов этого skill и есть такой запрос. Skill не коммитит, не стейджит и не мержит.

## Аргументы

`$ARGUMENTS` — `<название PR> [ветка]`:

- **название** — заголовок PR. Если содержит пробелы, пользователь берёт его в кавычки. Нужно
  в формате Conventional Commits на русском (`feat(web): экран бюджетов`), так как заголовок
  становится сообщением squash-коммита. Если передано в другом виде — предложить исправленный
  вариант и использовать его, только если пользователь не возражал.
- **ветка** — ветка, из которой открывается PR (head). Необязательна: по умолчанию текущая
  (`git branch --show-current`). Базовая ветка всегда `master`.

Если названия нет — остановиться и спросить, не придумывать самому.

## Порядок

1. Проверки до любых действий:
   - ветка не `master` (в него PR не открывают — правила веток в `CLAUDE.md`);
   - в рабочем дереве нет незакоммиченных изменений (`git status`) — если есть, предупредить,
     что в PR они не попадут, и спросить, продолжать ли;
   - у ветки есть коммиты относительно `master` (`git log master..<ветка>`), иначе PR пустой;
   - PR из этой ветки ещё не открыт (`gh pr list --head <ветка>`) — если открыт, показать ссылку
     и остановиться.
2. Прочитать `git log master..<ветка>` и `git diff master...<ветка> --stat`, чтобы описание
   отражало реальные изменения, а не только название.
3. Запушить ветку: `git push -u origin <ветка>`. Без `--force`.
4. Создать PR: `gh pr create --base master --head <ветка> --title "<название>" --body "<описание>"`.
5. Вернуть пользователю ссылку на PR.

## Описание PR

На русском, описание объясняет _зачем_ изменение, а не пересказывает дифф:

```
## Что и зачем

<1–3 предложения: проблема или задача и суть решения>

## Изменения

- <ключевые изменения по пакетам/модулям>

## Проверка

- <что запускалось: typecheck, lint, тесты; что проверено вручную>
- <что НЕ проверено — честно, если такое есть>
```

Если в `.claude/plans/` есть план, совпадающий с именем ветки, сослаться на него. В конце
описания — строка атрибуции из системных инструкций сессии, если она там задана.

## Ограничения

- Не использовать `--force`, `--no-verify`; не мержить PR и не удалять ветки — это отдельные
  явные просьбы.
- Не придумывать результаты проверок: в «Проверке» только то, что реально запускалось в сессии
  или видно из истории.
- Если `gh` не авторизован — остановиться и сообщить, предложить `! gh auth login`.
